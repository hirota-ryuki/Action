# ドキュメント一覧

このフォルダには、機能の設計や実装の経緯を説明するドキュメントを置いています。
新しい機能を作ったり、既存のコードを読み始めたりするときは、まずここから探してください。

---

## フォルダ構成

```
docs/
├── README.md              ← この一覧
├── 前提知識.md            ← 読む人が知っていること
├── ゲーム/                ← Action/Game（ゲーム固有の処理）
│   ├── 土台/              ← 起動・Game（ゲームの手順書はここから）
│   ├── キャラクター/      ← Player・Enemy 共通の部品（入力・モデル・状態異常・当たり判定）
│   │   ├── ステートマシン/  ← 項目のフォルダ（設計・手順・経緯・画像/）
│   │   └── …
│   ├── プレイヤー/        ← Player だけのもの（構成・ステート）
│   ├── カメラ/            ← GameCamera（寄り・俯瞰・一人称のモード）
│   ├── 敵/                ← Enemy だけのもの（ステート・黒騎士の AI）
│   ├── スキル/            ← スキルの共通の仕組み（SkillBase・SkillController・入力のボタン ActionButton）
│   ├── 魔法/              ← 魔法（MagicBase・氷・炎・燃える床・調整値 magic.json）
│   ├── UI/                ← 画面に出すもの（HUD・部品・UIManager）
│   ├── システム/          ← ゲーム全体で使う仕組み（JSON の読み込みなど）
│   ├── ステージ/          ← ボス戦の広間（消した草原のステージの経緯も）
│   └── アニメーション制作/ ← UE・動画からモーションを作る手順
├── エンジン/              ← Action/k2Engine・k2EngineLow（モデル読み込み・アニメーションなど）
│   ├── モデル読み込み/    ← 項目のフォルダ（エンジンは分野の直下に項目を置いてよい）
│   ├── デバッグUI/        ← ImGui を使った開発用の画面
│   └── ライティング/      ← アニメ調のライティング・影・鏡面反射
├── 最適化/                ← ゲームを軽く・速くするもの（ゲーム・エンジンどちらのコードでも）
│   ├── 最適化の方法/      ← 方法の一覧（ここから読む）
│   ├── 描画/              ← インスタンス描画・GPU の選び方・フレームレート
│   ├── 起動/              ← 起動時のモデルロード高速化・法線のキャッシュ
│   └── ステージ/          ← ステージ・ボス戦の広間の軽量化、テクスチャ
└── 開発環境/              ← .claude・.vscode（Claude の会話の引き継ぎ・スマホへの通知・開いたときの Pull）
```

分野（`ゲーム` / `エンジン` / `最適化` / `開発環境`）→ 機能 → 項目のフォルダに分けます。**1つの項目に1つのフォルダ**を作り、その中に次の3種類と、経緯で使う `画像/` を入れます。

| 種類 | ファイル名 | 何が書いてあるか | 読むとき |
|---|---|---|---|
| 設計 | `〇〇の設計.md` | 今のコードの構造・役割分担・実装方法・使い方。コードを変えたら一緒に直す | コードを読む前、機能を追加する前 |
| 手順 | `〇〇の手順.md` | 何もない状態から設計の形を作るまでの実装の手順。実装するときの順番で、1手順に1つずつ足していく | 自分で実装するとき、実装の流れを追いたいとき |
| 経緯 | `〇〇の経緯.md` | 何をして、どう確かめたか・なぜ今の形になったか。書き足していき、過去の記述は直さない | なぜ今の形になっているかを知りたいとき |

設計の冒頭には、経緯・手順があればそのリンクを置きます。

## 注意事項

- **骨の調整を層（`PoseLayers`）にまとめ、`Character::OnPostBodyLink()` をなくしました**（2026-11-19、[骨の調整の層の経緯](ゲーム/キャラクター/骨の調整の層/骨の調整の層の経緯.md)）。派生クラスの層は `OnAddPoseLayers()` で足します。[三人称の溜め撃ちの手順](ゲーム/プレイヤー/三人称の溜め撃ち/三人称の溜め撃ちの手順.md) は、まだ `OnPostBodyLink()` を書く形のままです。骨の調整の層の手順書は、まだ書いていません。[アニメーションの上半身の層の手順](エンジン/アニメーションの上半身の層/アニメーションの上半身の層の手順.md) は層が1枚のときの形で、2枚にする変更は経緯にだけあります。

- **魔法の強さを `magic.json` に出し、NPC の AI を距離の3段の形に作り直しました**（2026-11-17、[魔法の調整値の経緯](ゲーム/魔法/魔法の調整値/魔法の調整値の経緯.md)、[NPCのAIの経緯](ゲーム/キャラクター/NPCのAI/NPCのAIの経緯.md)）。[氷魔法の手順](ゲーム/魔法/氷魔法/氷魔法の手順.md)・[炎魔法の手順](ゲーム/魔法/炎魔法/炎魔法の手順.md)・[炎魔法発射後の燃える床の手順](ゲーム/魔法/炎魔法発射後の燃える床/炎魔法発射後の燃える床の手順.md) は、定数（`COOLDOWN`・`MakeSettings`・`FREEZE_SECONDS`・`MAX_CHARGE_SECONDS` など）を魔法のファイルに書く形のままです。その時点では正しく、[魔法の調整値の手順](ゲーム/魔法/魔法の調整値/魔法の調整値の手順.md)（24）が `magic.json` の値に置き換えます。[魔法の経緯](ゲーム/魔法/魔法の経緯.md)・[スキルの経緯](ゲーム/スキル/スキルの経緯.md)・[入力の経緯](ゲーム/キャラクター/入力/入力の経緯.md) などに書かれた `COOLDOWN`・`MakeSettings`・`fireHoldSeconds`・`NpcInputSource` の説明（射程に入ったら撃つだけの形）は、この変更より前の形です。

## ドキュメントを追加するとき

1. 分野（`ゲーム`・`エンジン`・`最適化`・`開発環境`）→ 機能 → **項目**の3段でフォルダを選ぶ。項目のフォルダ（例: `ゲーム/キャラクター/ステートマシン/`）に、その項目の設計・手順・経緯と `画像/` を入れる。
   - `ゲーム` の機能は `土台`・`キャラクター`・`プレイヤー`・`カメラ`・`敵`・`スキル`・`魔法`・`UI`・`システム`・`ステージ`・`アニメーション制作`。
   - ページが1つだけの項目も、項目のフォルダを作る。
   - 機能そのものの共通の仕組みのページ（`魔法/魔法の設計.md`・`スキル/スキルの設計.md`・`UI/UIの経緯.md` など、項目の名前が機能の名前と同じもの）は、機能のフォルダの直下に置く。
   - `エンジン`・`開発環境` は機能の段を飛ばし、分野の直下に項目のフォルダを置いてよい。
   - ゲームを軽く・速くするものは、ゲーム・エンジンどちらのコードでも `最適化` に置く。機能は `描画`・`起動`・`ステージ` と、方法の一覧の `最適化の方法`。
   - 合うフォルダがなければ作ってよい。
2. **設計は項目ごとに1ページ**にする。別の項目を、すでにある設計に書き足さない。
   - 例: 炎魔法を足したら、`魔法の設計.md` に章を足すのではなく `炎魔法の設計.md` を作る。
   - 共通の仕組みのページからは、各項目のページへリンクを張る。
   - 章は「全体像 → 詳細 → 実装方法 → 使い方 → 調整用の数値 → 決めたこと → 既知の課題 → 関連するページ」の順にする。無い章は飛ばしてよい。
   - 「実装方法」は必ず書く。**そのコードをどう書いたか**（データの持ち方、処理の組み立て、要所のコードの抜き出しと、そう書いた理由）を書く。使い方は書かない。
     - 抜き出したコードに、[前提知識](前提知識.md) で「よく知っている」にない関数・型・マクロが出てきたら、どこから来たもの（このゲーム・エンジン・C++ の標準ライブラリ・外部ライブラリ）と、何をするものかを一言添える。経緯の「ソースコードの問題箇所」「ソースコードの直し」も同じ。
   - 使い方（その仕組みを使って何かを足す・差し替える手順）は「使い方」の章に分けて書く。
   - 冒頭の説明のすぐ下に、方針を2〜3行の箇条書きで書く。以前の形や理由は「決めたこと」に回す。
   - 本文は **A4 1枚（図・表込みで 2,000〜2,500字）を目安**にする。調整値の表やコードの抜き出しは、はみ出してよい。
3. **経緯（何をした・どう調べた・前はどうだった）は設計に書かず、同じフォルダの `〇〇の経緯.md` に書く。**
   - 設計の冒頭（対象の行の下）に `経緯: [〇〇の経緯](〇〇の経緯.md)` を置く。経緯の冒頭には設計へのリンクを置く。
   - 経緯は日付ごとに書き足す。過去の記述（中身）は直さず、古くなった点はこの一覧の「注意事項」に書く。
   - ただし**書き方（用語・コマの書き方など）は、経緯も含めて全部のページでそろえる。** 書き方の決まりを変えたら、経緯のページも直す。
   - **不具合を直した・見た目を調整した項は、「1. 現状の問題 → 2. ソースコードの問題箇所 → 3. 直し方 → 4. ソースコードの直し → 5. どう確かめたか」の順に書く。**
     - 1 は、画面で何が起きているかを、ゲームの画像を付けて書く。
     - 2 は、問題のあるコードを抜き出し、どの行がなぜ問題かを書く。切り分けで試したことがあれば、試すごとの画像を付ける。
     - 3 は、どう直すかと、そうした理由を書く。
     - 4 は、直したコード（`diff`）と、**直す前と直した後の比較画像**（同じ場所・同じ向きで撮ったものを左右に並べる）を付ける。気になる所は拡大した画像も並べる。
     - 画像は、項目のフォルダの `画像/` に `〇〇_番号_何の画像か.jpg` の名前で置く（例: `画像/シャドウマップのクリア_1_直す前.jpg`）。横 1280 ピクセルの JPEG にする。
   - **エンジン（`k2Engine`・`k2EngineLow`）やシェーダーなど、もとからあるソースを改造・改良した項には、変更前（左）と変更後（右）を並べた比較の表を載せる**（Git のコンフリクト画面のように）。
     - 表は「行（変更前の行番号）・変更前・変更後」の3列にし、1行ずつ並べる。消す行は変更後を、足す行は変更前を空ける。場所を示すための変えない行は、両側に同じものを書く。
     - まとめて消すだけの長い関数は、最初と最後の行と「…（中身 N行）」で略してよい。ファイルごと消すものは、表にせず一覧にする。
4. **実装の方法は `〇〇の手順.md` に書く。** 上から順にやれば、設計に書いた最終形が必ず出来上がるようにする。
   - 冒頭に、設計・経緯へのリンクと、出来上がるもの・前提（ブランチ、使うライブラリの版など）を書く。
   - 「ヘッダー → CPP の順に上から説明する」形にしない。**実装するときの動きの順**に、「まずこれが要るので、〇〇.h にこれ、〇〇.cpp にこれを書く → 次はこれ」と書く。
   - 1つの手順で足すのは1つのことだけ。最初に「何のために足すか」を1〜2行で書く。
   - コードは、書く場所（ファイルと、どの関数の何の行の下か）がわかるように書く。あとの手順で、前の手順のコードを書き換えない。
   - **コードは少しずつ、行番号を付けて見せる。**（見本: [ステートマシンの手順](ゲーム/キャラクター/ステートマシン/ステートマシンの手順.md)）
     - 1回に足すのは10行くらいまで。新しいファイルも一度に全部は載せず、中身が空のクラスから始めて書き足していく。
     - 書く場所は「`State.h` の **9行目** `virtual ~State() = default;` の下に、4行足します（10〜13行目になります）」のように、行番号と、その行に書いてあることで示す。行番号は、それより前の手順を済ませたときの番号。
     - コードは「行番号の枠」と「コードの枠」を横に並べる表（`<table class="code-lines">`）に入れる。コードの枠には足す行だけを入れ、`+` や前後の行は入れない（枠をそのままコピーできるように）。見た目は `.vscode/markdown-preview.css` で付ける。
     - コードの下に「行・何をしているか」の表を置く。見ればわかる行（`{` や空の行など）は省く。
     - 新しく作ったファイルは、その手順の最後に全文を、同じ表で行番号を付けて載せる。
   - **読む人は、[前提知識](前提知識.md) に載っていることを知っていて、関数をたどって中身を読もうとする人**とする。どこまで説明するかは、前提知識に書いた知っている度合い（よく知っている・まあまあ・怪しい・微妙・導入方法を知らない）の決まりに合わせる。前提知識にないものは、知らない前提で書く。
   - **追加・削除・書き換え・コメントアウトした小手順には、「行・何をしているか」の表の下に「なぜ」と「効果」を1行ずつ書く。**
     - なぜ: そう書く（消す・変える）理由。ほかの書き方より何がよいか。
     - 効果: そうすると何ができるようになるか、何が防げるか。
   - **その下に「初めて出てくる名前」の表を置く。** 列は「ジャンル・名前・何のためのもの・何をするためのもの・どこから来たもの」。
     - ジャンルは `変数`・`メンバー変数`・`引数`・`関数`・`型`・`値`・`テンプレートの引数`・`マクロ`・`C++ の書き方` のどれか。コマンドを打って道具を動かす所（bash など）では、実行するプログラムは `コマンド`、環境変数は `環境変数`、コマンドに渡すものは `引数` にする。
     - コードに出てくる順に並べる。**そのページで初めて出てきたときだけ**載せ、あとの小手順では載せない。前提知識で「よく知っている」にあるものは載せない。
     - 「どこから来たもの」は、どれなのかがひと目でわかるように書く: `この手順で作る`／`〇〇の手順で作った（〇〇.h）`／`k2EngineLow（エンジン）の 〇〇.h`／`C++ の標準ライブラリ（<〇〇>。どこで読み込み済みか）`／`外部ライブラリ（名前）`／`C++ の書き方`／`使う側が決める`。エンジン・ライブラリのものは、そのヘッダーへのリンクを付ける。
     - 文は全部短く（1つの欄に1〜2文）。
   - **実装する人が触るところだけを書く。** Visual Studio が自動で書き換える `Game.vcxproj`・`Game.vcxproj.filters` などは書かない。手順と関係のない説明は書かない（「なぜ」「効果」「初めて出てくる名前」は要る説明）。
   - 各手順の終わりに「確かめ方」（ビルドが通る、起動して何が見えるか）を書く。
   - **どのファイルに何を足し、何を消し、何をコメントアウトしたかが、読んですぐわかるように書く。**
     - 冒頭に、全部の手順で触るファイルの一覧を置く（ファイル・新しく作る／書き足す／書き換える・どの手順か）。
     - 各手順の頭に「この手順で触るファイル」の表を置く。ファイルごとに「新しく作る」「追加」「削除」「コメントアウト」「書き換え」のどれをするかと、何をするかを書く。
     - 削除は、消す行を行番号の表で見せる（番号は消す前の番号）。コメントアウト・書き換えは、「前」と「後」の行番号の表を並べる（番号は、それぞれ変える前と変えた後の番号）。
     - 動きに関わるが、その手順では変えない**もとからあるコード**は「もとからある（変えない）」と書き分ける（例: FPS の上限を外すときの `#ifdef USE_FPS_LIMITTER` の分岐はエンジンにもとからあり、変えるのはマクロの1行だけ）。
   - すでに実装してある機能にも手順書を作る（設計1つに手順1つ）。手順書を作るために、今の実装は消さない・書き換えない。
     - 「その機能がまだない状態」から今のコードを作る手順にする。先に済ませておく手順書があれば、前提に書く。
     - 確かめるときは、作業用フォルダ（git worktree）でその機能のコードを外した状態を作り、手順どおりに組み込んで、ビルドが通ることと、出来上がったコードが今のコードと同じになることを見る。
   - 手順のコードは、別の作業用フォルダ（git worktree）で手順どおりに組み込み、ビルドが通ることを確かめてから書く。確かめた内容は経緯に書く。
5. ファイル名は**日本語のタイトル**にする。
   - スペースは使わない。区切りは `_` か `・` にする。
   - 例: `プレイヤーのステートの設計.md`、`プレイヤーのステートの経緯.md`
6. 冒頭に、タイトル・作成日・対象（ブランチや機能）を書く。
7. ソースコードへのリンクは、そのドキュメントからの相対パスで書く（例: `ゲーム/プレイヤー/` からなら `../../../Game/Source/...`）。
8. アニメーションのコマは「**クリップ名の N コマ目（何が起きるところか）**」と書く（例: `Run の 2コマ目（右足が前に着く）`）。`f02` のような略し方はしない。
   - コマは 30fps で、クリップの先頭を 0コマ目と数える。ページの中で一度そう書いておく。
   - アニメーションの1枚は「コマ」、ゲームの1回の更新は「フレーム」と書き分ける（「全フレームの平均」ではなく「全コマの平均」）。エンジンの用語の「キーフレーム」はそのまま。
9. **この一覧の表に1行追加する**。目的から引けるように、必要なら「目的から探す」の表にも追加する。
