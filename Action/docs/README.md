# ドキュメント一覧

このフォルダには、機能の設計や実装の経緯を説明するドキュメントを置いています。
新しい機能を作ったり、既存のコードを読み始めたりするときは、まずここから探してください。

---

## フォルダ構成

```
docs/
├── README.md              ← この一覧
├── ゲーム/                ← Action/Game（ゲーム固有の処理）
│   ├── キャラクター/      ← Player・Enemy 共通の部品（入力・モデル・状態異常・当たり判定）
│   ├── プレイヤー/        ← Player だけのもの（構成・ステート）
│   ├── 敵/                ← Enemy だけのもの（ステート）
│   ├── 魔法/              ← 魔法と弾
│   ├── UI/                ← 画面に出すもの（HUD・部品・UIManager）
│   ├── システム/          ← ゲーム全体で使う仕組み（JSON の読み込みなど）
│   ├── ステージ/          ← 地形・岩・木・草の作り方と描き方
│   └── アニメーション制作/ ← UE・動画からモーションを作る手順
└── エンジン/              ← Action/k2Engine・k2EngineLow（描画・モデル読み込みなど）
    ├── デバッグUI/        ← ImGui を使った開発用の画面
    └── ライティング/      ← アニメ調のライティング（トゥーン陰影・リムライト・アウトラインなど）
```

分野（`ゲーム` / `エンジン`）→ 機能のフォルダに分け、1つのフォルダに次の3種類を並べます。

| 種類 | ファイル名 | 何が書いてあるか | 読むとき |
|---|---|---|---|
| 設計 | `〇〇の設計.md` | 今のコードの構造・役割分担・実装方法・使い方。コードを変えたら一緒に直す | コードを読む前、機能を追加する前 |
| 手順 | `〇〇の手順.md` | 何もない状態から設計の形を作るまでの実装の手順。実装するときの順番で、1手順に1つずつ足していく | 自分で実装するとき、実装の流れを追いたいとき |
| 経緯 | `〇〇の経緯.md` | 何をして、どう確かめたか・なぜ今の形になったか。書き足していき、過去の記述は直さない | なぜ今の形になっているかを知りたいとき |

設計の冒頭には、経緯・手順があればそのリンクを置きます。

## 一覧

ゲームのコードを初めて読むときは、入口の [キャラクターの構成](ゲーム/キャラクター/キャラクターの構成.md) から始めてください。部品の一覧から各ページへ進めます。
どの設計も「全体像 → 詳細 → 実装方法（どう書いたか） → 使い方（足し方・差し替え方） → 調整用の数値 → 決めたこと → 既知の課題」の順に並んでいます。

## ドキュメントを追加するとき

1. 分野（`ゲーム` か `エンジン`）→ 機能（`ゲーム` なら `キャラクター`・`プレイヤー`・`敵`・`魔法`・`ステージ`・`アニメーション制作`）でフォルダを選ぶ。
   - 合うフォルダがなければ作ってよい。`エンジン` はページが少ないうちは分野の直下に置く。
2. **設計は項目ごとに1ページ**にする。別の項目を、すでにある設計に書き足さない。
   - 例: 炎魔法を足したら、`魔法と弾の設計.md` に章を足すのではなく `炎魔法の設計.md` を作る。
   - 共通の仕組みのページからは、各項目のページへリンクを張る。
   - 章は「全体像 → 詳細 → 実装方法 → 使い方 → 調整用の数値 → 決めたこと → 既知の課題 → 関連するページ」の順にする。無い章は飛ばしてよい。
   - 「実装方法」は必ず書く。**そのコードをどう書いたか**（データの持ち方、処理の組み立て、要所のコードの抜き出しと、そう書いた理由）を書く。使い方は書かない。
   - 使い方（その仕組みを使って何かを足す・差し替える手順）は「使い方」の章に分けて書く。
   - 冒頭の説明のすぐ下に、方針を2〜3行の箇条書きで書く。以前の形や理由は「決めたこと」に回す。
   - 本文は **A4 1枚（図・表込みで 2,000〜2,500字）を目安**にする。調整値の表やコードの抜き出しは、はみ出してよい。
3. **経緯（何をした・どう調べた・前はどうだった）は設計に書かず、同じフォルダの `〇〇の経緯.md` に書く。**
   - 設計の冒頭（対象の行の下）に `経緯: [〇〇の経緯](〇〇の経緯.md)` を置く。経緯の冒頭には設計へのリンクを置く。
   - 経緯は日付ごとに書き足す。過去の記述（中身）は直さず、古くなった点はこの一覧の「注意事項」に書く。
   - ただし**書き方（用語・コマの書き方など）は、経緯も含めて全部のページでそろえる。** 書き方の決まりを変えたら、経緯のページも直す。
4. **実装の方法は `〇〇の手順.md` に書く。** 上から順にやれば、設計に書いた最終形が必ず出来上がるようにする。
   - 冒頭に、設計・経緯へのリンクと、出来上がるもの・前提（ブランチ、使うライブラリの版など）を書く。
   - 「ヘッダー → CPP の順に上から説明する」形にしない。**実装するときの動きの順**に、「まずこれが要るので、〇〇.h にこれ、〇〇.cpp にこれを書く → 次はこれ」と書く。
   - 1つの手順で足すのは1つのことだけ。最初に「何のために足すか」を1〜2行で書く。
   - コードは、書く場所（ファイルと、どの関数の何の行の下か）がわかるように書く。あとの手順で、前の手順のコードを書き換えない。
   - 各手順の終わりに「確かめ方」（ビルドが通る、起動して何が見えるか）を書く。
   - **どのファイルに何を足し、何を消し、何をコメントアウトしたかが、読んですぐわかるように書く。**
     - 冒頭に、全部の手順で触るファイルの一覧を置く（ファイル・新しく作る／書き足す／書き換える・どの手順か）。
     - 各手順の頭に「この手順で触るファイル」の表を置く。ファイルごとに「新しく作る」「追加」「削除」「コメントアウト」「書き換え」のどれをするかと、何をするかを書く。
     - 削除・コメントアウト・書き換えは、前と後のコードを並べる（`diff` のコードブロックで、消す行は `-`、足す行は `+`）。
     - 動きに関わるが、その手順では変えない**もとからあるコード**は「もとからある（変えない）」と書き分ける（例: FPS の上限を外すときの `#ifdef USE_FPS_LIMITTER` の分岐はエンジンにもとからあり、変えるのはマクロの1行だけ）。
   - すでに実装してある機能にも手順書を作る（設計1つに手順1つ）。手順書を作るために、今の実装は消さない・書き換えない。
     - 「その機能がまだない状態」から今のコードを作る手順にする。先に済ませておく手順書があれば、前提に書く。
     - 確かめるときは、作業用フォルダ（git worktree）でその機能のコードを外した状態を作り、手順どおりに組み込んで、ビルドが通ることと、出来上がったコードが今のコードと同じになることを見る。
   - 手順のコードは、別の作業用フォルダ（git worktree）で手順どおりに組み込み、ビルドが通ることを確かめてから書く。確かめた内容は経緯に書く。
5. ファイル名は**日本語のタイトル**にする。
   - スペースは使わない。区切りは `_` か `・` にする。
   - 例: `プレイヤーのステートの設計.md`、`プレイヤーのステートの経緯.md`
6. 冒頭に、タイトル・作成日・対象（ブランチや機能）を書く。
7. ソースコードへのリンクは、そのドキュメントからの相対パスで書く（例: `ゲーム/プレイヤー/` からなら `../../../Game/Source/...`）。
8. アニメーションのコマは「**クリップ名の N コマ目（何が起きるところか）**」と書く（例: `Run の 2コマ目（右足が前に着く）`）。`f02` のような略し方はしない。
   - コマは 30fps で、クリップの先頭を 0コマ目と数える。ページの中で一度そう書いておく。
   - アニメーションの1枚は「コマ」、ゲームの1回の更新は「フレーム」と書き分ける（「全フレームの平均」ではなく「全コマの平均」）。エンジンの用語の「キーフレーム」はそのまま。
9. **この一覧の表に1行追加する**。目的から引けるように、必要なら「目的から探す」の表にも追加する。
