# モデル読み込みと法線スムージングの設計

作成日: 2026-11-05
対象: `k2EngineLow` のモデル読み込み（FBX→tkm 変換、tkm 読み込み、BSP による法線スムージング）
関連コミット: `31fbca03 <Loading>起動時のモデルロードを高速化(BSP探索の空ループ削除・FBX変換時の重複頂点統合)`

このドキュメントでは、`ModelRender::Init()` にモデルを渡してから描画できる状態になるまでに、エンジンの中で何が行われているかを説明します。
起動時間に大きく関わる部分なので、モデル読み込み・FBX インポーター・BSP を触るときは先に読んでください。

---

## 1. 全体の流れ

```
ModelRender::Init("xxx.FBX" または "xxx.tkm")
 │
 ├─ ① FbxRuntimeImporter::ResolveToTkmFilePath()
 │     .fbx なら、必要なときだけ tkm/tks に変換して、tkm のパスを返す（.tkm ならそのまま返す）
 │
 └─ ② Model::Init()
       ├─ tkm バンクにあればそれを使う（同じモデルを2回目以降に読むときは ③ を飛ばす）
       └─ ③ TkmFile::Load()
             ├─ 頂点・インデックスを読む（ファイルの法線は使わず、ここで計算し直す）
             ├─ ④ 面の法線から頂点の法線を作る
             ├─ ⑤ BSP で「同じ座標の頂点」を探して法線を平均する（スムージング）
             └─ 接ベクトル・従ベクトルを作る
```

| 段階 | 処理 | コード |
|---|---|---|
| ① | FBX→tkm/tks/tka 変換とキャッシュ判定 | [FbxRuntimeImporter.cpp](../../../k2EngineLow/tkFile/FbxRuntimeImporter.cpp) |
| ② | tkm バンクの確認 | [Model.cpp](../../../k2EngineLow/graphics/Model.cpp) |
| ③〜⑤ | tkm 読み込みと法線スムージング | [TkmFile.cpp](../../../k2EngineLow/tkFile/TkmFile.cpp) の `Load()`、`BuildTangentAndBiNormal()` |
| ⑤ | 同じ座標の頂点の探索 | [BSP.cpp](../../../k2EngineLow/geometry/BSP.cpp) |

## 2. FBX→tkm 変換とキャッシュ

FBX を渡したときは、毎回変換するのではなく、**ファイルの更新日時を比べて必要なときだけ変換**します。

| 出力 | 作り直す条件 | 関数 |
|---|---|---|
| `xxx.tkm` / `xxx.tks` | tkm が無い、または FBX の方が新しい | `ResolveToTkmFilePath()` → `IsConversionNeeded()` |
| アニメーションの `xxx.tka` | tka が無い、アニメーション FBX の方が新しい、またはスケルトン（tks）の方が新しい | `ResolveAnimationFbxToTka()` |
| テクスチャの `xxx.dds` | dds が無い、または元画像の方が新しい | `ConvertTextureToDDS()`（texconv.exe を起動） |

> **注意: インポーターのコードを変えても、既存の tkm は作り直されません。**
> 判定は日付だけなので、変換処理を直したときは対象の `.tkm` を手で消してから起動してください。
> 変換された tkm/tks/tka は git で管理しているので、作り直したらコミットします。

## 3. 頂点の統合（FBX インポーター）

### 3.1 なぜ必要か

FBX と GPU では、「頂点」の単位が違います。

| | 位置 | 法線・UV |
|---|---|---|
| FBX | 頂点ごとに1つ | **面の角（corner）ごと**に持つ（同じ頂点でも面によって違うことがある） |
| GPU（tkm） | 位置・法線・UV・スキンを**まとめて1つの頂点**として扱う | |

角ごとにそのまま頂点を作ると、同じ頂点が何個も重複します。SK_Player では、頂点数がインデックス数と同じ 124,521 個になっていました。

### 3.2 どうまとめているか

`FbxRuntimeImporter::BuildMeshParts()` で、角ごとに作った頂点を `VertexKey` に詰め、ハッシュマップで重複を調べます。

- **比べる属性**: 座標・法線・UV・スキンウェイト・ボーン番号（tkm に保存されるものすべて）
- **どれか1つでも違えば別の頂点**にする。UV の継ぎ目や、法線が分かれた角ばった部分は、そのまま別の頂点として残ります。
- **マップはメッシュごと**に持つ。1つのメッシュの頂点バッファは、そのメッシュのすべてのマテリアル（インデックスバッファ）で共有しているためです。
- 比較は `memcmp`、ハッシュは FNV-1a で、どちらもバイト列に対して行います。`VertexKey` は全メンバが4バイト型でパディングがありません。これを `static_assert` で確かめています。メンバを増やすときは、パディングが入らないようにしてください。
- 浮動小数点をバイト単位で比べるので、`0.0` と `-0.0` は別の頂点になります。まとまらないだけで、表示がおかしくなることはありません。

### 3.3 効果（SK_Player.FBX）

| | 統合前 | 統合後 |
|---|---|---|
| 頂点数 | 124,521 | **28,493** |
| インデックス数（ポリゴン数×3） | 124,521 | 124,521 |
| SK_Player.tkm のサイズ | 7.5MB | 2.1MB |

## 4. tkm 読み込み時の法線スムージング

`TkmFile::Load()` は、**ファイルに入っている法線を使わず**、読み込むたびに法線を計算し直します（`vertex.normal = g_vec3Zero` で捨てている）。

1. **面の法線を足し込む**（`NormalSmoothing::Execute()`）
   三角形ごとに面の法線を求め、その三角形の3頂点に足して正規化します。インデックスで共有されている頂点は、周りの面の平均になります。
2. **同じ座標の頂点どうしで平均する**（`BuildTangentAndBiNormal()`、`isFlatShading == false` のときだけ）
   頂点ごとに BSP で「座標がまったく同じ頂点」を探します。法線の向きが近い（内積が正の）ものだけを足して平均します。UV の継ぎ目などで分かれた頂点も、ここで滑らかにつながります。
   4スレッドに分けて実行します。

手順 2 は頂点の数だけ BSP を探索するので、**BSP の探索が速いことが前提**になっています（次章）。

## 5. BSP（二分空間分割）

### 5.1 役割

点の集まりを平面で2つに分けることを繰り返し、木にしたものです。「この座標にある頂点はどれか」を、全部の頂点を調べずに探せます。

エンジン内での使い道は次の2つです。

- `TkmFile`: 法線スムージングで、同じ座標の頂点を探す（4章）
- `NaviMesh`: セルの中心座標から近いセルを探す（[NaviMesh.cpp](../../../k2EngineLow/AI/PathFinding/NaviMesh.cpp)）

### 5.2 構築（`BSP::Build()`）

1. 点の集まりの中心と共分散行列を求める。
2. ヤコビ法で固有ベクトルを求め、**一番散らばっている方向**を法線とする平面で2つに分ける。
3. 分けた両側に対して、同じことを繰り返す。
4. 散らばりがほぼ無くなったら（ほぼ同じ場所の点だけになったら）、その点をまとめて末端（`SLeafList`）にする。

| 要素 | 持っているもの |
|---|---|
| `SNode` | 分割平面、左右の子、中心座標 |
| `SLeaf` | 座標と、付加データ（TkmFile では法線へのポインタ） |
| `SLeafList` | ほぼ同じ場所にある `SLeaf` の配列 |

### 5.3 探索（`BSP::WalkTree()`）

座標が平面の左右どちらにあるかを判定して、片方の子だけに進みます。末端に着いたら、そこにある点ごとにコールバックを呼びます。
1回の探索で通るノードは木の深さぶん（12万点で約17個）なので、全頂点を探索しても **O(N log N)** で済みます。

### 5.4 書き換えるときの注意

- `WalkTree()` は頂点の数だけ呼ばれます。**探索の中に、ノードが持つ点の数に比例する処理を入れないでください。** 全体が O(N²) になります。
- `WalkTree()` は再帰関数なので、引数（`shared_ptr` と `std::function`）は const 参照で受け取っています。値渡しに戻すと、ノードを1つ下りるたびにコピーが発生します。
- `toolsProj/nvmExporter/nvmExporter/bsp/` に同じ BSP の古いコピーがあります。こちらは修正前のままです（空ループが残っています）。

## 6. 既知の課題

- **起動直後の数秒はシェーダーのコンパイル**: `Shader::Load()` は起動のたびに `D3DCompileFromFile` でコンパイルし、`K2_DEBUG` では最適化なしになります（[Shader.cpp](../../../k2EngineLow/graphics/Shader.cpp)）。さらに速くするなら、コンパイル結果のキャッシュが候補です。
- 起動が遅かった原因と直した経緯は [起動時のモデルロード高速化 実装レポート](../../02_実装レポート/エンジン/起動時のモデルロード高速化_実装レポート.md) にあります。
