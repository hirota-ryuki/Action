## 2026-11-08 今のゲームのコードから、手順書を書いた

### 何をしたか

「FPS を解放したのはどうやったのか、どこのヘッダーや CPP に何を足して、何を消したりコメントアウトしたのか全くわからない」との指摘を受けて、手順書の決まりに「触るファイルの一覧」「この手順で触るファイル」の表と、書き換える行の diff を足した。そのうえで、すでに実装してある機能にも、設計書1つに手順書1つを作った。

**用語:**

| 用語 | 何のことか |
|---|---|
| diff | 変更前と変更後の違いを、消す行（`-`）と足す行（`+`）で並べて見せる書き方 |

ゲームのコードは、部品どうしが頼り合っている（`Character.h` は入力・移動・モデル・状態異常・当たり判定・魔法をすべて持ち、`Game.cpp` はキャラクター・カメラ・UI を作る）。そのため、機能を1つずつ別々に外すことはできない。テンプレートのままの空の `Game` から、今のゲームまでを1本の流れにして、22本に分けた。

| 決めたこと | 理由 |
|---|---|
| 順番は「土台 → キャラクターの構成 → 陣営と当たり判定 → 入力 → NPCのAI → 移動 → モデル → 状態異常 → ステートマシン → 敵のステート → プレイヤーの構成 → プレイヤーのステート → ダッシュ → 走りから止まる → 魔法と弾 → 弾 → 氷魔法 → 炎魔法 → 炎魔法発射後の燃える床 → UIの構成 → HUD → FPSの表示」 | あとの手順書が使うものを、先の手順書で作る順。たとえばステートマシンは凍結（状態異常）を前提にし、弾は当たり判定の一覧から相手を探す |
| 土台（`Game`・`Stage`）の設計書を新しく作った | 今まで設計書がなく、1本目の手順書の行き先がなかった |
| カメラ（`GameCamera`）はプレイヤーの構成、ステージに置く炎（`FireEffect`）は炎魔法に入れた | どちらも専用の設計書がなく、それぞれの設計書のフォルダー構成・魔法の説明で触れられているため |
| 今の形に書き換わるまでの、途中だけの行を使った | 例: NPCのAIができるまでの「何も入力しない入力元」、ステートマシンができるまでの `m_mover.Update(m_input, deltaTime);`、手順が進むたびに書き足す `Game::Start()` の優先度のコメント。どれも後の手順書で「削除」「書き換え」として diff に出している |
| アニメーション制作（UE・Python の作業手順）の手順書は作らない | ユーザーの判断。C++ に関わるクリップの登録は、プレイヤーのステート・ダッシュ・走りから止まるの手順書に入れた |

### どう確かめたか

リポジトリとは別の作業用フォルダー（main を `git worktree` で取り出したもの）で確かめた。今の実装は消していない（作業用フォルダーの中だけで外して戻した）。

1. 今のコードの各行が、どの手順で現れるかを表にした（作業用のツールで、行の番号で指定する）。表から、各手順の時点のソースと、手順書の diff・新しく作るファイルの中身・触るファイルの表を作った。手で写さないので、手順書のコードは今のコードと一字一句同じ。
2. 土台の前（テンプレートのままの `Game`）から FPS の表示の最後まで、73の時点のソースを順に書き出し、そのたびに `Game.sln` を Debug x64 でビルドした。すべて通った。最後の時点は main と差がなかった。
   - 途中で1回、本当のビルドエラーが見つかった。プレイヤーのステートの手順1で、`PlayerConfig.cpp` がクリップの番号（`PlayerAnimator.h`）を読めなかった（`PlayerState.h` を経由して読むため）。クリップの登録を手順2に移して直した。
3. できた手順書を、別のツールで逆から読み取って（diff を逆に当て、新しく作るファイルの中身が手順書と同じことを確かめてから消す）、FPS の表示から土台まで戻した。戻した形は、1 で作った土台の前の状態と一致した。
4. ゲームの画面での確かめはしていない。どの手順書も、最後まで進めると今のコードと同じになるので、出来上がったときの動きは今のゲームと同じ。途中の「確かめ方」に書いた見え方（たとえば「Enemy が Idle で立つ」）は、まだ画面で見ていない。

**用語:**

| 用語 | 何のことか |
|---|---|
| Debug x64 | Visual Studio のビルドの設定の名前。Debug はデバッグ用、x64 は 64ビット向け |

### まだ確かめていないこと

- 各手順の「確かめ方」に書いた画面の見え方。
- `player-json` ブランチ（プレイヤーの調整値を `player.json` から読む）をマージしたあとの形。マージしたら、プレイヤーの構成・プレイヤーのステート・ダッシュ・走りから止まる・キャラクターモデルの手順書を直す。

## 2026-11-09 ステートマシンの手順書を、新しいファイルを少しずつ書き足す形に書き直した

### 何をしたか

「手順書が抽象的すぎる。行番号がなかったり、コードが一気に何行も書かれたりしていて理解できない」との指摘を受けた。読むのは学生で、手順書のコードは Claude が組み込んで確かめる。まず [ステートマシンの手順](../../キャラクター/ステートマシン/ステートマシンの手順.md) だけを書き直して、見てもらうことにした。

| 決めたこと | 理由 |
|---|---|
| 新しいファイルは、中身が空のクラスから始め、1回に10行くらいずつ足す（`State.h` は 1-2〜1-7 の6回、`StateMachine.h` は 2-2〜2-14 の13回） | 37行・99行を一度に載せると、どの行が何のためにあるのかが追えない |
| 足す場所は「〇行目 `その行に書いてあること` の下」と書き、足したあとの行番号も書く。行番号は、それより前の小手順を全部済ませたときの番号 | 行番号だけだと書き間違いに気づけず、書いてあることだけだと同じ行が2つあるときに迷う |
| `diff` の中には行番号を入れない | ユーザーの判断。行の頭に番号を入れると、コードをそのまま写せない |
| コードの下に、行ごとの「何をしているか」の表を置く。見ればわかる行は省く | コードの中のコメントだけでは、学生には足りない |
| 各手順の最後に、出来上がったファイルの全文と、どの行をどの小手順で足したかの表を置く | 自分の書いたものと見比べるため |
| `Game.vcxproj`・`Game.vcxproj.filters` には行番号を書かない | Visual Studio が自動で書き足し、入る位置はそれまでに足した順番で変わるため |
| 前の小手順で書いた行は書き換えない。足すだけにする | 手順書の決まり（途中の手順で足したコードを、あとで書き換えない） |

### どう確かめたか

1. 今の `State.h`・`StateMachine.h` の各行を、どの小手順で足すかを決め、そこから小手順ごとの途中の形（`State.h` 6個、`StateMachine.h` 13個）と、手順書の `diff` を作業用のツールで作った。手で写していないので、手順書のコードは今のコードと一字一句同じ。
2. 作業用フォルダー（main を `git worktree` で取り出したもの）で、途中の形を1つずつ置き、確かめ用の `.cpp` と一緒に Game.vcxproj の設定（Debug / x64、Visual Studio 18 の MSBuild）でコンパイルした。19個とも通った。テンプレートは使われるまで中身がコンパイルされないので、確かめ用の `.cpp` では仮の `Id`・`Context` でクラスを明示的に実体化した。最後の形では、仮のステートを `Register` して `Init`・`Update`・`Reset` まで呼んだ。
   - 確かめ用の `.cpp` が本当にコンパイルされているかは、わざとエラーになる行を入れて、そこで止まることで確かめた（最初は MSBuild へのファイルの渡し方が違っていて、何もコンパイルされずに「通った」と出ていた。渡し方を直してから、全部やり直した）。
3. できた手順書を別のツールで読み取って、空のファイルから `diff` を順に当てた。2つとも今のコードと同じになった。本文に書いた「〇行目の下に〇行足す（〇〜〇行目になる）」の19か所も、実際に当てた位置と同じだった。
4. ゲーム全体のビルドと画面での確かめはしていない。最後の形が今のコードと同じなので、出来上がったときの動きは今のゲームと同じ。

**用語:**

| 用語 | 何のことか |
|---|---|
| MSBuild | Visual Studio のビルドを、コマンドから動かすための道具 |
| 明示的に実体化 | テンプレートは使われるまで中身がコンパイルされないので、`template class 名前<...>;` と書いて、コンパイルさせること |

### まだ確かめていないこと

- ほかの手順書は、まだ前の形のまま。この形でよければ、決まりを CLAUDE.md と README に書き、順に直す。
- 手順書の前提に書いた「Visual Studio 2022」は、プロジェクトのツールセット（v145）と合っていない（v145 は Visual Studio 18 のもの）。

**用語:**

| 用語 | 何のことか |
|---|---|
| ツールセット | Visual Studio がビルドに使うコンパイラなどの一式。プロジェクトの設定に `v145` のように版が書いてある |

### 追記: 実装する人が触るところだけにした

「`Game.vcxproj`・`Game.vcxproj.filters` は書かなくていい。実装する人が触る場所に限って書き、余計な情報は消す」との指摘を受けて、ステートマシンの手順書から次を消した。コードは変えていないので、組み立て直すと今のコードと同じになること（19か所の行番号も含む）を、もう一度確かめた。

- `Game.vcxproj`・`Game.vcxproj.filters` の `diff` と、触るファイルの表のその行（Visual Studio が自動で書き足すので、実装する人は触らない）
- 冒頭の「確かめた記録」へのリンク、作成日、「main からブランチを切る」
- 出来上がったファイルの全文の下の「どの行をどの小手順で足したか」の表
- 読み方とテンプレートについての説明の重なり

### 追記: コードの左に行番号を並べた

「コードの横にも行番号を書いてほしい。ただ、コピーしたときに `+` や番号が入らないようにしたい」との指摘を受けて、`diff` をやめ、行番号の枠とコードの枠を横に並べる形にした（上の「`diff` の中には行番号を入れない」は、この形に置き換わった）。

| 決めたこと | 理由 |
|---|---|
| HTML の表（`<table class="code-lines">`）の左の列に行番号、右の列に足すコードだけを入れる。前後のもとからある行は枠に入れず、文で「〇行目 `…` の下」と示す | コードの枠をそのままコピーでき、`+` も番号も入らない |
| 見た目は `.vscode/markdown-preview.css` で付け、`.vscode/settings.json` の `markdown.styles` で読み込む | VSCode のプレビューに CSS を足す方法がこれしかない。ただ、`.vscode/` はPCごとの設定として git に入れていない（`settings.json` に絶対パスがある）ので、今はこの PC にだけある。ほかの PC にどう配るかは、まだ決めていない |
| 番号の枠もコードと同じ色付けの枠にし、表の中の文字の大きさ・1行の高さ・余白を CSS で固定する。長い行は折り返さず、枠の中で横にスクロールさせる | 枠の作りが違ったり、日本語の行の高さが違ったり、折り返したりすると、番号とコードの行がずれた（ユーザーに VSCode のプレビューで見てもらって、3回直した） |
| VSCode の標準のプレビュー（`Ctrl+Shift+V`）で読む | 拡張機能 Office Viewer の表示では、表の幅の指定が効かず、コードが途中で切れた。この PC では、ユーザー設定に `"workbench.editorAssociations": { "*.md": "default" }` を足して、`.md` をテキストで開くようにした（リポジトリには入れていない） |

**用語:**

| 用語 | 何のことか |
|---|---|
| CSS | HTML の見た目（色・大きさ・余白）を決める言語。ここでは、プレビューの表の見た目を付けるのに使う |
| Office Viewer | VSCode の拡張機能の名前。`.md` などを Word のような見た目で開く |

コードは変えていないので、手順書を読み取って空のファイルから組み立て直し、今のコードと同じになること、19か所の行番号が合っていることを、もう一度確かめた。

## 2026-11-09 手順書33本を、行番号を付けて少しずつ足す形に書き直した

### 何をしたか

ステートマシンの手順書で決めた形（1回に10行くらいまで、行番号の枠とコードの枠を並べる表、足す場所を「〇行目 `…` の下」で示す、実装する人が触るところだけを書く）で、残りの手順書も全部書き直した。ゲームの手順書25本（README の「ゲームを作る順番」の 0〜23 と、JSON読み込み）と、エンジンの手順書7本。

| 決めたこと | 理由 |
|---|---|
| 消す・書き換えるところは、消す行を枠で、書き換えは「前」と「後」の枠を並べて見せる | NPCのAIの手順書で見てもらい、この形でよいと言われた |
| ゲームの手順書は、小手順の見出しと行ごとの説明の表を手で書いた | 読むのは学生なので、1つずつ何のためのコードかを書く |
| エンジンの手順書7本は、小手順の分け方と見出し（足すコードのコメントか、関数の名前）を道具で付け、手順ごとの説明は前の手順書の文を残した | モデル読み込みだけで小手順が140を超え、手で説明の表を書くと終わらないため。行ごとの説明の表は付けていない |
| 前提の「Visual Studio 2022 で」を「Visual Studio で」にした | プロジェクトのツールセット（v145）は Visual Studio 18 のもので、2022 ではビルドできないため |
| 前提の「作業を始める前に、main からブランチを切る」を消した | 実装する人が触るところではないため |

### どう確かめたか

作業用の道具（スクラッチの Python）で、次を確かめた。ビルドはし直していない。

1. **始まる前の形と、手順ごとの形を出した。** ゲームの手順書は、デバッグUIを入れる直前の main（#84 `a5df75c1`）のコードから、前の形の手順書の `diff` を逆にたどって、テンプレートのままの `Game` まで戻した。そこから手順書を1本ずつ前へ当て、手順書ごと・手順ごとの形を出した。前の形の手順書は、書き直しを始めた時点の main（#92 `dc5869e7`）のものを読んだ。
   - JSON読み込みの手順書は、手順5・6の `diff` にファイルの印がないので、読むときだけ `JsonFile.cpp` の印を足した。
   - デバッグUIの手順書は `diff` で書かれていないので、「入れる前」を #84、「入れたあと」を #85（`680d6e24`）のコードから取った。
   - エンジンの手順書は、#92 のコードから、その手順書の `diff` を逆にたどって「始まる前」を出した。ファイルの印がない `diff` は、すぐ前の文にあるソースへのリンクでファイルを決めた。
2. **書き直した手順書を読み取って組み立て直した。** 始まる前の形に、手順書の枠（足す・消す・書き換えの前と後）を上から当てて、終わったあとの形と一字一句同じになることを、33本すべてで確かめた。本文の「〇行目の下に〇行足します（〇〜〇行目になります）」も、全部、枠の番号と合っていた。
3. **手順の区切りの形を前の手順書と合わせた。** 各手順の終わりの形が、前の形の手順書の同じ手順の終わりの形と同じになることを、デバッグUI以外の手順書で確かめた（ゲームの土台の手順1の終わりで空の行が1つ違っていたので直した）。前の形の手順書は各手順の終わりでビルドを確かめてあるので、書き直した手順書も各手順の終わりでビルドが通る。
   - デバッグUIの手順書は、前の形の手順書から手順ごとの形を読み取れないので、手順の区切りは説明に合わせて決めた。最後の形が #85 と同じことだけを確かめ、手順の途中でのビルドは確かめていない。

### まだ確かめていないこと

- 書き直した手順書どおりに手で組み込んで、各手順の終わりでビルドすること（上の 3 で、前の形と同じであることは確かめてある）。
- エンジンの手順書の見出しは道具で付けたので、意味の取りにくいものがある（「`〇〇()` の続きを書く」など）。

## 2026-11-16 手順書に「なぜ」「効果」と「初めて出てくる名前」の表を足す決まりにした

### 何をしたか

手順書を読んだ人から、「知らない関数が出てきても、エンジンの機能なのかライブラリの機能なのか、なぜそこで使うのかがわからない」「足したり消したりしたときに、なぜそうするのか・何がよくなるのかを書いてほしい」と言われた。README の「ドキュメントを追加するとき」の4に次を足し、[ステートマシンの手順](../../キャラクター/ステートマシン/ステートマシンの手順.md) をこの形に直した。

| 決めたこと | 理由 |
|---|---|
| 小手順ごとに「なぜ」「効果」を1行ずつ書く | 「何をしているか」の表だけでは、そう書く理由と、書いて何ができるようになるかがわからない |
| 「初めて出てくる名前」の表（ジャンル・名前・何のためのもの・何をするためのもの・どこから来たもの）を置く | どこから来たもの（このゲーム・エンジン・標準ライブラリ・C++ の書き方）がわかれば、関数をたどって中身を読みに行ける |

## 2026-11-17 残りの手順書32本に「なぜ」「効果」と「初めて出てくる名前」の表を足した

### 何をしたか

| 用語 | 何のことか |
