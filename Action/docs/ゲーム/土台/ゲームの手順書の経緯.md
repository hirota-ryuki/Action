## 2026-11-08 今のゲームのコードから、手順書を書いた

### 何をしたか

「FPS を解放したのはどうやったのか、どこのヘッダーや CPP に何を足して、何を消したりコメントアウトしたのか全くわからない」との指摘を受けて、手順書の決まりに「触るファイルの一覧」「この手順で触るファイル」の表と、書き換える行の diff を足した。そのうえで、すでに実装してある機能にも、設計書1つに手順書1つを作った。

ゲームのコードは、部品どうしが頼り合っている（`Character.h` は入力・移動・モデル・状態異常・当たり判定・魔法をすべて持ち、`Game.cpp` はキャラクター・カメラ・UI を作る）。そのため、機能を1つずつ別々に外すことはできない。テンプレートのままの空の `Game` から、今のゲームまでを1本の流れにして、22本に分けた。

| 決めたこと | 理由 |
|---|---|
| 順番は「土台 → キャラクターの構成 → 陣営と当たり判定 → 入力 → NPCのAI → 移動 → モデル → 状態異常 → ステートマシン → 敵のステート → プレイヤーの構成 → プレイヤーのステート → ダッシュ → 走りから止まる → 魔法と弾 → 弾 → 氷魔法 → 炎魔法 → 燃える床 → UIの構成 → HUD → FPSの表示」 | あとの手順書が使うものを、先の手順書で作る順。たとえばステートマシンは凍結（状態異常）を前提にし、弾は当たり判定の一覧から相手を探す |
| 土台（`Game`・`Stage`）の設計書を新しく作った | 今まで設計書がなく、1本目の手順書の行き先がなかった |
| カメラ（`GameCamera`）はプレイヤーの構成、ステージに置く炎（`FireEffect`）は炎魔法に入れた | どちらも専用の設計書がなく、それぞれの設計書のフォルダー構成・魔法の説明で触れられているため |
| 今の形に書き換わるまでの、途中だけの行を使った | 例: NPCのAIができるまでの「何も入力しない入力元」、ステートマシンができるまでの `m_mover.Update(m_input, deltaTime);`、手順が進むたびに書き足す `Game::Start()` の優先度のコメント。どれも後の手順書で「削除」「書き換え」として diff に出している |
| アニメーション制作（UE・Python の作業手順）の手順書は作らない | ユーザーの判断。C++ に関わるクリップの登録は、プレイヤーのステート・ダッシュ・走りから止まるの手順書に入れた |

### どう確かめたか

リポジトリとは別の作業用フォルダー（main を `git worktree` で取り出したもの）で確かめた。今の実装は消していない（作業用フォルダーの中だけで外して戻した）。

1. 今のコードの各行が、どの手順で現れるかを表にした（作業用のツールで、行の番号で指定する）。表から、各手順の時点のソースと、手順書の diff・新しく作るファイルの中身・触るファイルの表を作った。手で写さないので、手順書のコードは今のコードと一字一句同じ。
2. 土台の前（テンプレートのままの `Game`）から FPS の表示の最後まで、73の時点のソースを順に書き出し、そのたびに `Game.sln` を Debug x64 でビルドした。すべて通った。最後の時点は main と差がなかった。
   - 途中で1回、本当のビルドエラーが見つかった。プレイヤーのステートの手順1で、`PlayerConfig.cpp` がクリップの番号（`PlayerAnimator.h`）を読めなかった（`PlayerState.h` を経由して読むため）。クリップの登録を手順2に移して直した。
3. できた手順書を、別のツールで逆から読み取って（diff を逆に当て、新しく作るファイルの中身が手順書と同じことを確かめてから消す）、FPS の表示から土台まで戻した。戻した形は、1 で作った土台の前の状態と一致した。
4. ゲームの画面での確かめはしていない。どの手順書も、最後まで進めると今のコードと同じになるので、出来上がったときの動きは今のゲームと同じ。途中の「確かめ方」に書いた見え方（たとえば「Enemy が Idle で立つ」）は、まだ画面で見ていない。

### まだ確かめていないこと

- 各手順の「確かめ方」に書いた画面の見え方。
- `player-json` ブランチ（プレイヤーの調整値を `player.json` から読む）をマージしたあとの形。マージしたら、プレイヤーの構成・プレイヤーのステート・ダッシュ・走りから止まる・キャラクターモデルの手順書を直す。
