ゲームの手順書（[ゲームの土台の手順](ゲームの土台の手順.md) から [FPSの表示の手順](../UI/FPSの表示の手順.md) までの22本）を、どう分けて、どう確かめたかの記録です。日付ごとに書き足します。

## 2026-11-08 今のゲームのコードから、手順書を書いた

### 何をしたか

「FPS を解放したのはどうやったのか、どこのヘッダーや CPP に何を足して、何を消したりコメントアウトしたのか全くわからない」との指摘を受けて、手順書の決まりに「触るファイルの一覧」「この手順で触るファイル」の表と、書き換える行の diff を足した。そのうえで、すでに実装してある機能にも、設計書1つに手順書1つを作った。

ゲームのコードは、部品どうしが頼り合っている（`Character.h` は入力・移動・モデル・状態異常・当たり判定・魔法をすべて持ち、`Game.cpp` はキャラクター・カメラ・UI を作る）。そのため、機能を1つずつ別々に外すことはできない。テンプレートのままの空の `Game` から、今のゲームまでを1本の流れにして、22本に分けた。

| 決めたこと | 理由 |
|---|---|
| 順番は「土台 → キャラクターの構成 → 陣営と当たり判定 → 入力 → NPCのAI → 移動 → モデル → 状態異常 → ステートマシン → 敵のステート → プレイヤーの構成 → プレイヤーのステート → ダッシュ → 走りから止まる → 魔法と弾 → 弾 → 氷魔法 → 炎魔法 → 燃える床 → UIの構成 → HUD → FPSの表示」 | あとの手順書が使うものを、先の手順書で作る順。たとえばステートマシンは凍結（状態異常）を前提にし、弾は当たり判定の一覧から相手を探す |
| 土台（`Game`・`Stage`）の設計書を新しく作った | 今まで設計書がなく、1本目の手順書の行き先がなかった |
| カメラ（`GameCamera`）はプレイヤーの構成、ステージに置く炎（`FireEffect`）は炎魔法に入れた | どちらも専用の設計書がなく、それぞれの設計書のフォルダー構成・魔法の説明で触れられているため |
| 今の形に書き換わるまでの、途中だけの行を使った | 例: NPCのAIができるまでの「何も入力しない入力元」、ステートマシンができるまでの `m_mover.Update(m_input, deltaTime);`、手順が進むたびに書き足す `Game::Start()` の優先度のコメント。どれも後の手順書で「削除」「書き換え」として diff に出している |
| アニメーション制作（UE・Python の作業手順）の手順書は作らない | ユーザーの判断。C++ に関わるクリップの登録は、プレイヤーのステート・ダッシュ・走りから止まるの手順書に入れた |

### どう確かめたか

リポジトリとは別の作業用フォルダー（main を `git worktree` で取り出したもの）で確かめた。今の実装は消していない（作業用フォルダーの中だけで外して戻した）。

1. 今のコードの各行が、どの手順で現れるかを表にした（作業用のツールで、行の番号で指定する）。表から、各手順の時点のソースと、手順書の diff・新しく作るファイルの中身・触るファイルの表を作った。手で写さないので、手順書のコードは今のコードと一字一句同じ。
2. 土台の前（テンプレートのままの `Game`）から FPS の表示の最後まで、73の時点のソースを順に書き出し、そのたびに `Game.sln` を Debug x64 でビルドした。すべて通った。最後の時点は main と差がなかった。
   - 途中で1回、本当のビルドエラーが見つかった。プレイヤーのステートの手順1で、`PlayerConfig.cpp` がクリップの番号（`PlayerAnimator.h`）を読めなかった（`PlayerState.h` を経由して読むため）。クリップの登録を手順2に移して直した。
3. できた手順書を、別のツールで逆から読み取って（diff を逆に当て、新しく作るファイルの中身が手順書と同じことを確かめてから消す）、FPS の表示から土台まで戻した。戻した形は、1 で作った土台の前の状態と一致した。
4. ゲームの画面での確かめはしていない。どの手順書も、最後まで進めると今のコードと同じになるので、出来上がったときの動きは今のゲームと同じ。途中の「確かめ方」に書いた見え方（たとえば「Enemy が Idle で立つ」）は、まだ画面で見ていない。

### まだ確かめていないこと

- 各手順の「確かめ方」に書いた画面の見え方。
- `player-json` ブランチ（プレイヤーの調整値を `player.json` から読む）をマージしたあとの形。マージしたら、プレイヤーの構成・プレイヤーのステート・ダッシュ・走りから止まる・キャラクターモデルの手順書を直す。

## 2026-11-08 プレイヤーの調整値の手順書につなげた

ゲームの手順書を書いている間に、プレイヤーの調整値を `player.json` から読む変更（#84）と、その手順書 [プレイヤーの調整値の手順](../プレイヤー/プレイヤーの調整値の手順.md) が main に入った。この手順書は、数値をコードに直接書いた `PlayerConfig.cpp`（#84 の前の形）から始まるので、ゲームの手順書の最後（FPSの表示の手順）の続きにあたる。README の「ゲームを作る順番」の 22 に足した。

0〜21 の手順書は #84 の前のコードで書いたままにした。モデルと剣のパスは `const char*` で持ち、22 の手順1で `std::string` に変わるので、キャラクターモデル・プレイヤーの構成の手順書の前提に書いた。

どう確かめたか: 作業用フォルダーで、#84 の前の main（0〜21 を最後まで進めた形と同じ）に、プレイヤーの調整値の手順書の diff と新しいファイルを1手順ずつ当て、そのたびに Game.sln を Debug x64 でビルドした。手順の前と手順1〜9の10回とも通った。最後は、Game のソースも `player.json` も、今の main（#84）と同じになった。

## 2026-11-09 ステートマシンの手順書を、新しいファイルを少しずつ書き足す形に書き直した

### 何をしたか

「手順書が抽象的すぎる。行番号がなかったり、コードが一気に何行も書かれたりしていて理解できない」との指摘を受けた。読むのは学生で、手順書のコードは Claude が組み込んで確かめる。まず [ステートマシンの手順](../キャラクター/ステートマシンの手順.md) だけを書き直して、見てもらうことにした。

| 決めたこと | 理由 |
|---|---|
| 新しいファイルは、中身が空のクラスから始め、1回に10行くらいずつ足す（`State.h` は 1-2〜1-7 の6回、`StateMachine.h` は 2-2〜2-14 の13回） | 37行・99行を一度に載せると、どの行が何のためにあるのかが追えない |
| 足す場所は「〇行目 `その行に書いてあること` の下」と書き、足したあとの行番号も書く。行番号は、それより前の小手順を全部済ませたときの番号 | 行番号だけだと書き間違いに気づけず、書いてあることだけだと同じ行が2つあるときに迷う |
| `diff` の中には行番号を入れない | ユーザーの判断。行の頭に番号を入れると、コードをそのまま写せない |
| コードの下に、行ごとの「何をしているか」の表を置く。見ればわかる行は省く | コードの中のコメントだけでは、学生には足りない |
| 各手順の最後に、出来上がったファイルの全文と、どの行をどの小手順で足したかの表を置く | 自分の書いたものと見比べるため |
| `Game.vcxproj`・`Game.vcxproj.filters` には行番号を書かない | Visual Studio が自動で書き足し、入る位置はそれまでに足した順番で変わるため |
| 前の小手順で書いた行は書き換えない。足すだけにする | 手順書の決まり（途中の手順で足したコードを、あとで書き換えない） |

### どう確かめたか

1. 今の `State.h`・`StateMachine.h` の各行を、どの小手順で足すかを決め、そこから小手順ごとの途中の形（`State.h` 6個、`StateMachine.h` 13個）と、手順書の `diff` を作業用のツールで作った。手で写していないので、手順書のコードは今のコードと一字一句同じ。
2. 作業用フォルダー（main を `git worktree` で取り出したもの）で、途中の形を1つずつ置き、確かめ用の `.cpp` と一緒に Game.vcxproj の設定（Debug / x64、Visual Studio 18 の MSBuild）でコンパイルした。19個とも通った。テンプレートは使われるまで中身がコンパイルされないので、確かめ用の `.cpp` では仮の `Id`・`Context` でクラスを明示的に実体化した。最後の形では、仮のステートを `Register` して `Init`・`Update`・`Reset` まで呼んだ。
   - 確かめ用の `.cpp` が本当にコンパイルされているかは、わざとエラーになる行を入れて、そこで止まることで確かめた（最初は MSBuild へのファイルの渡し方が違っていて、何もコンパイルされずに「通った」と出ていた。渡し方を直してから、全部やり直した）。
3. できた手順書を別のツールで読み取って、空のファイルから `diff` を順に当てた。2つとも今のコードと同じになった。本文に書いた「〇行目の下に〇行足す（〇〜〇行目になる）」の19か所も、実際に当てた位置と同じだった。
4. ゲーム全体のビルドと画面での確かめはしていない。最後の形が今のコードと同じなので、出来上がったときの動きは今のゲームと同じ。

### まだ確かめていないこと

- ほかの手順書は、まだ前の形のまま。この形でよければ、決まりを CLAUDE.md と README に書き、順に直す。
- 手順書の前提に書いた「Visual Studio 2022」は、プロジェクトのツールセット（v145）と合っていない（v145 は Visual Studio 18 のもの）。

### 追記: 実装する人が触るところだけにした

「`Game.vcxproj`・`Game.vcxproj.filters` は書かなくていい。実装する人が触る場所に限って書き、余計な情報は消す」との指摘を受けて、ステートマシンの手順書から次を消した。コードは変えていないので、組み立て直すと今のコードと同じになること（19か所の行番号も含む）を、もう一度確かめた。

- `Game.vcxproj`・`Game.vcxproj.filters` の `diff` と、触るファイルの表のその行（Visual Studio が自動で書き足すので、実装する人は触らない）
- 冒頭の「確かめた記録」へのリンク、作成日、「main からブランチを切る」
- 出来上がったファイルの全文の下の「どの行をどの小手順で足したか」の表
- 読み方とテンプレートについての説明の重なり
